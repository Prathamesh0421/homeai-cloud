# Contract and design changelog

Record every change to `02_CONTRACTS.md`, a component's API section, or a D2 design decision.
Format: `YYYY-MM-DD — <component(s)> — <change> — agreed by <names>`.

## Baseline (Deliverable #3 plan, 2026-11-02)
Additions to the D2 design made by this plan (all marked **[D3 addition]** in the component plans):
- C1: `GET /feeds/stats` for C4 dashboards; `device-uploader` service client; `house_id` accepted on `POST /houses` only in DEMO_MODE (fixed seed IDs).
- C2: `POST /alert-rules/defaults`, `POST /alert-rules/subscriptions/sync`, ContactSubscriptionSync job, `trigger_label` column on `alert_types`, `next_attempt_at` on `notifications`, DEMO_MODE `view_link` in alert detail; `GET /alerts` also accepts service scope `alerts:read`.
- C3: model registry (`/models*`, `model_evaluations` table, model status), `POST /inference/test`, `GET /models/deployment` + `worker_heartbeats`, `GET /detections/stats`, `handoff_status` field; max worker attempts fixed at 3.
- C4: `GET /auth/revoked`, `POST /dashboard/rollup`, `users_public` view, service clients table.
- Platform: all IDs UUID strings; RS256 + JWKS; quiet hours suppress only medium/low; sensitivity ±0.10.

## Changes
- 2026-11-11 — C3 — Evaluating a model always refreshes its metrics, but only promotes `registered` to `evaluated`; an `active` or `retired` model keeps its lifecycle status so re-evaluation cannot silently remove the live deployment. — agreed by Renuka (C3 owner)
- 2026-11-03 — C2 — Added `GET /alert-rules/{id}` (cloud_staff) so the `Location` header of `POST /alert-rules` resolves; rule responses carry `ETag: "<version>"` for `If-Match`. `POST /alert-rules/defaults` takes `{tenant_id}` in the body (as in the API table). — agreed by Prathamesh (C2 owner)
- 2026-11-03 — C2 — Rule selection (C2 plan §4.1 step 4): per alert type the most specific applicable rule wins for the detection's room (room rule > whole-house rule > tenant default). A room-only house rule replaces the default only in its room; a disabled house rule does not hide the default. — agreed by Prathamesh (C2 owner)
- 2026-11-03 — C2 — RuleEngine (C2 plan §4.1 step 6): the label is checked before the service, so `service_disabled` is only reported when a rule for the detected label exists but its service is off (previously any disabled service turned every unmatched detection into `service_disabled`). Thresholds are rounded to 2 decimals after the sensitivity shift (avoids 0.55+0.10 float drift). — agreed by Prathamesh (C2 owner)
- 2026-11-03 — C2 — C2-06: migration 0003 adds `c2.alerts.threshold` (effective threshold at raise time, rule + house sensitivity) shown as `evidence.threshold`; `GET /alerts/{id}` adds `allowed_actions[]` and `evidence.detection_available` (false → labels fall back to the alert's top label when C3 is unavailable); `house_name`/`room_name` are null when C1 is unavailable instead of failing the request; `false_positive` also sets `resolved_at`; stats keys: day = UTC `YYYY-MM-DD`, severity ordered critical→low, others by count. — agreed by Prathamesh (C2 owner)
- 2026-11-03 — C2 — C2-09: alert email subjects are ASCII (`[HomeAI] CRITICAL Smoke alarm - Maple St`, accents stripped, < 100 chars) because SNS rejects non-ASCII subjects; notification retries are at most 3 attempts in total (+1 min, +2 min), resolving the plan's "backoff 1, 2, 4 min" vs "attempt_count < 3"; the in-app notification row has `attempt_count = 1`. — agreed by Prathamesh (C2 owner)
- 2026-11-04 — Platform (init.sql, C4, C1, CI) — Reader grants follow contract §5.1 exactly: `init.sql` no longer gives `c2_reader` every c1/c4 table or `c3_reader` every c4 table (they could read `c4.users.password_hash` and `c4.service_clients.secret_hash`); C4 migration 0002 grants the allowed tables/columns; C1's 0001 must grant `c1.houses, c1.rooms` to `c2_reader` (C1 plan §2.1). Mongo `c2_reader` is limited to `find` on `ai_detections`. C4 migration 0001 no longer runs `CREATE SCHEMA IF NOT EXISTS` (fails as `c4_app`), the C4 container stops if a migration fails, and CI runs every migration round-trip as the owner role. — agreed by Prathamesh (C2, P0-11); changes in Renuka's (`infra/`) and Mohit's (`services/c4_dashboard/`) files, for their review
- 2026-11-04 — C3 — Re-classify keeps the detection's `_id` (Mongo rejects a replacement that changes `_id`; with a stable `detection_id` C2 answers `duplicate` instead of raising a second alert for the same clip). A clip whose detection was stored by an earlier, failed attempt is now finished (handoff re-sent, marked `analyzed`) instead of staying `processing` forever. — agreed by Prathamesh (C2 owner); change in Renuka's files, for her review
- 2026-11-04 — C2 — C2-10 jobs (C2 plan §4.5): NotificationRetry stops for good when the alert is `false_positive` or `resolved` (`last_error=alert_closed`) or the contact was removed in C4 (`contact_removed`), sends to the contact's current email, does not use up an attempt while C4 is unavailable, and also delivers email rows left `queued` for 5 min (crash between insert and send). ContactSubscriptionSync also cleans houses that lost all contacts (found by their topic). `POST /alert-rules/subscriptions/sync` answers 409 `sync_in_progress` while the job runs. When a contact's email changes, the subscription of the old address (same `contact_id` filter policy) is removed as soon as the new one is created, so the old address stops receiving that contact's emails. A retry that fails with an unexpected error counts as an attempt. — agreed by Prathamesh (C2 owner)
- 2026-11-04 — C2 — `POST /alert-rules/subscriptions/sync` response adds `failed` (houses skipped because SNS failed, tried again on the next run) to `{topics, subscribed, pending, removed}`. — agreed by Prathamesh (C2 owner)
